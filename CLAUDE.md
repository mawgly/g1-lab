# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local, Windows-only MuJoCo reinforcement-learning lab, made of two Python packages:

- `arm_sim/`: the original SO-101 arm reaching experiment (Gymnasium env + SB3 PPO). It is self-contained and writes to `runs/so101`.
- `humanoid_sim/`: the "Robot RL Lab". It covers Humanoid-v5 walking, being extended into a multi-robot lab (Unitree G1 29-DoF, SO-101 as a fixed-base check), with a local browser UI, an experiment queue and CPU / GPU-physics / full-GPU training backends.

The user's language is Russian. Write all user-facing text in Russian: README.ru.md/HUMANOID.md (`README.md` is the English one for GitHub, with `LICENSE` Apache-2.0 and `THIRD_PARTY.md`), browser UI strings, the `ValueError` messages in `lab.py`/`lab_api.py`/`webapp.py` that are shown in the browser, the journal. Code identifiers and most code comments are in English.

The browser UI also comes in English and Simplified Chinese (EN / 中文 / RU buttons in the site header, remembered in `localStorage`); Russian stays the default and the source of truth, and the CLI, agents and files on disk stay Russian:
- **Interface strings** (gettext style, `humanoid_sim/i18n.py`): the Russian text is the key of its translation in `humanoid_sim/web/i18n/en.json` and `zh.json`, which the browser (`web/i18n.js`: `t('…')`, `tn(n, 'шаг|шага|шагов')`, `translatePage()` for static HTML) and the server share. `{name}` is a text placeholder, `{n}`, `{n1}`… a number; a message formatted from a template is matched back (`Выберите от 1 до {n} дорожек`). The browser asks with `?lang=en|zh` (`withLang`, also on SSE and the report frame); `webapp.py` then translates `{'error': …}` replies, `/api/lab` names/notes/queue errors, `/api/lab/robots` labels, journal, race/playback frames (per-language frame JSON) and renders `report.html` from `report.json` (`reports.render_report(report, lang)`). Without `lang`, everything is Russian, bit for bit as before. **A new Russian string in a page, a script, a `ValueError`/label in `webapp.py`, `lab.py`, `lab_api.py`, `lab_worker.py`, `tasks/catalog.py`, `tasks/config.py` (G1 parameter labels), `goal_check.items` or `reports.py` needs its English and Chinese in both catalogs**: `tests/test_i18n.py` lists what is missing, and `journal_translate export` puts it into the next batch for the translator (below).

## Architecture (humanoid_sim)

**Processes and file-based IPC.** Everything coordinates through files in run directories, not through sockets:
- `webapp.py` (`ThreadingHTTPServer`, localhost only, Host/Origin checked) serves the site (`/` = `web/site.html`, plus `journal.html`, `lab.html`, `race.html`) and a JSON/SSE API; `python -m humanoid_sim.site_export --out <folder> [--zip <file>]` writes the same pages as a static copy for public hosting (data snapshots per language, the media they reference, no lab controls, no live race). It runs live playback of saved stages (`Playback`, one per experiment, at most 12; `/api/state|model|frame|stream|control`) and the stage race (`Race` per robot/task, 1–10 `RaceLane`s = (branch, stage or `'latest'`) stepped in lockstep with one seed and one scenario command, at most 2 races; `/api/race/model|frame|stream|control?robot=…`), and hands lab actions to `Laboratory` / `LabJobs`. Both players share `_Looping` (tick thread that runs only while an SSE client is subscribed). Browser side: one site in one look (`site.css`; `site.js` gives the header/footer and `data()`, the live `/api/lab/…` or a static export's `data/<name>.<lang>.json`): Home `site.html`, Journal `journal.html` and Lab `lab.html` + `labtree.js`, the read-only branch tree of one robot (parent → child, verdicts and notes from the snapshot, stages, steps, the running branch's progress) with, live only, links to each branch's `report.html?experiment=…` and to the race. The browser has no training controls any more (the old `lab.js`/`lab.css` tabs «Смотреть», «Обучать», «История запусков» are gone); the lab's agents and scripts call the POST endpoints `/api/lab/create|series|enqueue|start|stop|job` themselves. `web/viewer3d.js` builds the Three.js scene for `race.js` (`race.html?robot=…&task=…[&focus=…][&add=<branch>]`, standalone, with a link back to `lab.html`; `add` appends that branch's newest stage as a lane next to those already racing, the oldest giving way at 10; a lane spec `'latest'` follows new checkpoints) and `app.js` (`index.html?experiment=…[&live=1]`, the single stage player kept for tasks without `playback.follow_body`, i.e. the arm; catalog field `race` tells `labtree.js` which to link).
- `Laboratory.start()` launches `lab_worker.py` as a detached process. The worker drains `runs/humanoid_lab/queue.json` one job at a time. For each job it spawns `humanoid_sim.cli train --config run_config.json` with the interpreter chosen by backend (`lab_worker.training_interpreter`: `cpu`→current, `gpu`/`full_gpu`→`.venv-fullgpu`). The worker survives the server and the browser closing.
- `LabJobs` runs one-off jobs (`lab_tasks.py`: report, diagnostics, motion, command_suite, benchmarks) as subprocesses.
- Locks: `core.RunLock` is an `msvcrt` byte-range lock on `<dir>/trainer.lock` (Windows-only, released by the OS if a process crashes). Lock dirs in use: each run dir (trainer), `<lab>/worker`, `<lab>/compute` (serializes heavy work: held by the queue worker, lab jobs, and manual `cli train` runs without `--config`), `<lab>/job`, `<lab>/queue-edit`. "Is it running?" is answered by trying the lock, not by trusting `status.json`.
- Stopping works by touching `stop.request` (in the run dir, or in the lab root for the whole queue). `StageCallback._on_step` checks for it, then the trainer saves a stage and exits.

**Run directory layout.** `runs/humanoid` is the original experiment ("baseline"). It is read-only from the lab: no enqueue, only branching from it. Lab experiments live in `runs/humanoid_lab/exp-<16 hex>/` with `experiment.json` (manifest, written last), `run_config.json`, `status.json`, `stage_XXXXXXXXXXXX/`, `session_*/` (SB3 CSV logs), `report.{json,html}` and `training.log`. A branch copies the source stage into its new dir. `lab.validate_config` is the single schema for experiment configs (`DEFAULTS`, bounds, `PRESETS` baseline/careful/explore). `create_series` produces 3 presets × seeds 42/43/44.

**Stages (checkpoints).** `core.save_stage` writes `policy.zip` + `normalize.pkl` + `metadata.json` into a `.pending-*` dir, then renames it. `list_stages` ignores incomplete dirs. Always write JSON with `core.write_json` (atomic temp + `os.replace` with retries for Windows sharing violations). The policy and the VecNormalize stats are one unit; never load one without the other. Stage retention (user decision 20.10): new G1 branches save every 10 M steps (`every` is bounded 100 k–50 M); a finished branch, once written up in the journal (a race of ~5 progress stages), is thinned with `python -m humanoid_sim.prune <branch> --apply`, which keeps 5 evenly spread stages plus the report's best/last, branch points, journal lanes and stages its notes mention, and moves the rest to the Windows Recycle Bin (never a hard delete; running branches and baseline are refused). `StageCallback` saves a stage every `every` steps at rollout boundaries, CPU-evaluates it (`core.evaluate_stage`, fixed seeds from 60000) and refreshes the report.

**Robot / task / backend registries.** Robot and task are independent choices, and they're registered in code only (never imported from browser input):
- `robots/registry.py` `RobotSpec`, `tasks/registry.py` `TaskSpec`, with built-ins registered in `tasks/catalog.py::registries()` (lru-cached; builds each env once to read joint/actuator names). Pairs: `humanoid`/`humanoid_v5`, `so101`/`arm_reach` (reuses `arm_sim.env.ArmReachEnv`), `g1_29dof`/`g1_velocity` (`tasks/g1_velocity.py`, torque-limited PD on top of `assets/robots/g1`), and `g1_12dof`/`g1_velocity`: the legs-only G1, derived at load time from the same 29-DoF files with MjSpec (waist/arm joints removed, so those links are welded; `LEGS_ONLY_REVISION` is part of its checkpoint identity). G1 `task_config` also has `commands` (training speed range, stand share, sideways and turn ranges, and `straight_probability`: the share of walking commands with no turn, which under heading hold keep the heading they start at — added 21.10 because with turns drawn uniformly from ±yaw_rate the policy never learned to walk straight and its no-command drift wandered 0.02–0.08 rad/s between stages; Unitree's G1 trains turns within ±0.2 rad/s only). `stand_heading_hold` (missing = true, the original task; new runs false) decides whether heading hold also steers a stand command: with it, a standing robot turned more than ~11° got a turn-in-place command above `STAND_SPEED`, so the reward treated it as moving (standing terms off, gait asking for steps) and it shuffled backwards; false keeps a stand command exactly zero, as Isaac Lab does. `side_heading_hold` (missing = true, the original task; new runs false; added 23.10 for iteration 26) does the same for a purely sideways command (`pure_sideways` of the requested command: vx 0, no turn): false keeps its turn exactly zero in `effective_command`, as g1_ctrl's stick gives it, so the yaw and `yaw_drift` terms see the whole drift. Under the hold, a ±1 m/s side step drifted ~0.12 rad/s on its own. The policy answered the hold's ~0.025 rad/s turn command 3–5 times over, so ω_z stayed near 0 and `yaw_drift` saw only ~0.02, while on the robot the drift showed in full (0.10–0.16 rad/s; critic, `hold_probe.py`). Commands and reward only, identity unchanged; branch with `scripts/lab/task_branch.py <parent> side_heading_hold false <name> <note>`.
- `tasks.catalog.make_task` always builds a **CPU** Gym env. Batched tensor envs for `full_gpu` are separate adapters in `backends/registry.py`, keyed by (robot_id, task_id, backend). They must not silently fall back to CPU. `TaskSpec.training_backends` is what the UI/validator allow. G1 has a tensor env registered for testing, but its public backends are CPU-only until the CUDA checks pass.
- `TaskSpec.label` and `TaskSpec.jobs` (which `lab_tasks` checks apply) are served by `/api/lab/robots`; `lab_api` gates jobs on them (and `labtree.js` reads the task's `race`), so don't add `robot_id`/`task_id` string checks in shared code.
- `TaskSpec.config_validator` normalizes `task_config` (G1: `reward_weights`). The config is saved into stage metadata, and evaluation/playback use the checkpoint's saved config, not the current one.
- G1 (`g1_velocity`, obs-v2): observation/reward/command equations live only in `tasks/g1_tensor_math.py` and are used by both `tasks/g1_velocity.py` (CPU, float64 batch of 1) and `g1_tensor_env.py` (CUDA). Change them there, never in one backend. Commands resample during training episodes; commands passed via `reset(options={'command': ...})` or `set_command()` stay fixed (evaluation scenarios rely on this). Throughput reference: `lab/g1_full_gpu_benchmark.json` (`python -m humanoid_sim.g1_benchmark` in `.venv-fullgpu`).
- G1 reward weight `feet_flat` (default 0, added 22.10): −w·Σ over both feet of sin² of the `ankle_roll_link` tilt (`foot_rotation` from `xmat`, both backends; the frame is level in the home pose on the floor), every step, standing and walking. Why: contact is judged by the ankle_roll origin height (< `CONTACT_HEIGHT` 0.05), and a foot on its heel with the toe up > 20° lifts it above that, so gait/swing/slip missed the support and the robot shuffled on one heel (toe up 46–52°). A reward weight only: identity and branching are unchanged.
- G1 `task_config.sole_contact` (default false, added 22.10): the reward's contact (gait, swing mask, slip) is the lowest sole point < `SOLE_CONTACT_HEIGHT` 0.01 instead of the ankle_roll origin < `CONTACT_HEIGHT` 0.05 (`g1_tensor_math.sole_height`: min over each foot's four 5 mm collision spheres of centre z − radius, from `geom_xpos` in both backends; ≈ −0.6 mm standing flat, whatever the tilt). Why: after `feet_flat` the heel foot still stood toe up 20–23°, and the old rule missed 64–78% of its real stance. A foot hovering below 1 cm counts as support, so shuffling earns no gait credit for swing. The swing height term still measures the ankle_roll origin; `goal_check` "missed stance" and `scripts/lab/probes/foot_contact.py` still describe the old rule. Reward only: identity and branching are unchanged.
- G1 reward weight `clearance` (default 0, added 22.10, held for iteration 5): unitree_rl_mjlab `feet_clearance` (weight −1 there, target 0.10 at the foot sites, which lie on the sole bottom), −w·Σ over both feet of |`sole_height` − `CLEARANCE_HEIGHT` 0.10|·`foot_speed` (ankle_roll origin xy displacement over the control step / dt), only while `moving` (theirs: ‖v_xy‖ + |ω| > 0.1). Linear in height and gated by foot speed, so it pulls a travelling foot up at 1.5–3 cm, where under `sole_contact` only the quadratic swing term did. The backends pass `sole_height` when `sole_contact` is on or this weight is non-zero, and pass `sole_contact` explicitly, so the contact rule does not change with it. Reward only: identity and branching are unchanged.
- G1 reward weight `yaw_drift` (default 0, added 22.10 for iteration 6): −w·|e| on straight walking commands only (`straight_walking` of the requested command, before heading hold), e = `yaw_drift_update` EMA of ω_z − c (pelvis `velocity[:, 2]`, c the rewarded command after `effective_command`), e ← e + (dt/τ)(ω_z − c − e), τ = `YAW_DRIFT_SECONDS` 1.2. Why: without a turn command the drift stayed 0.07–0.13 rad/s (goal < 0.05); under heading hold the arc is steered away, so ω_z − c averages to the arc's offset, which the exp yaw term (flat near zero) barely charged. State `yaw_drift_error` (n,) in both envs, updated before the reward only while the weight is non-zero (off: no state, reward bit for bit the old one), zeroed at reset, on resampling (CUDA: per world mask) and by `set_command` / `options['command']`. Full GPU logs `rollout/yaw_drift_abs` (mean |e| on straight commands per rollout, `TensorG1Env.rollout_metrics` read by `TensorPPO.collect`) while the weight is on. Reward only: identity and branching are unchanged.
- G1 `task_config.random_phase` (missing = false; new runs true; added 22.10 for iteration 7): a training reset starts the gait clock at a random step of its cycle (CUDA: `phase_offset` per world, drawn in `_masked_reset`, `_phase()` = lengths + offset; CPU: `phase_steps` drawn in `reset` when no `options['command']`/`'phase_steps'` is given), so episodes start on either foot. Before it every episode started at phase 0 (left foot first); goal_check's right-foot start (a reset half a cycle on) was a state training never saw and drifted −0.05…−0.11 rad/s, while the same start after a moment of standing drifted like the left one. - G1 `task_config.action_limit` (default 1) sets the action box: target = home + scale·clip(action, ±limit), still clipped to real joint ranges and torque limits. A limit other than 1 is a different contract (`action_schema` `g1_velocity:action-v2-limitN` via `TaskSpec.config_identity`), so `task_identity(robot, task, task_config)` takes the run's or stage's task config.
- G1 actions are clipped to the action box before the PD target, so without limits the entropy bonus grows the policy std without bound (seen: σ 1e10, every joint a random bang-bang switch). New G1 full-GPU runs set `max_std` (std cap) and `bounds_coef` (rl_games bounds loss on the action mean); `supervise` prints the clipped-action share and σ. `mirror_coef` (default 0) adds the rsl_rl-style mirror loss for the real-robot profile: `symmetry.Mirror` derives the left/right joint pairs and signs from the model's joint axes and mirrors the deploy observation (gait phase shifted half a cycle); `tests/test_symmetry.py` checks the map against the physics. Added 20.10 because PPO kept a right-turning bias (policy asymmetry grew from 0.21 to ~5, mostly the arms). `range_bounds` (default false) makes the bounds loss use, per joint, the action where the motor target reaches the joint's range instead of the ±action_limit box (G1 knees, waist and ankles were commanded far past their range, 99–100% at the limit); use it with a small `bounds_coef` (0.001 — at 0.01 the sudden loss of ~8 broke walking within 8 M steps). A joint whose range lies beyond the action box is bounded at ±action_limit/`BOUND` (`full_gpu_train.range_bounds`), so its loss starts exactly where the action is clipped (22.10: bounded at ±action_limit, the loss began at 1.1·limit, and the G1 left wrist pitch mean sat in that dead zone at +10.3…+11.5 for 400 M steps, its target stuck at +40°; only the four wrist pitch/yaw joints are affected).
- `full_gpu_train.py` + `tensor_ppo.py` (`TensorPPO`, `TensorNormalize`): rollouts and PPO updates on CUDA via `tensor_env.TensorHumanoidEnv` / `g1_tensor_env.TensorG1Env`. They still save SB3-compatible `policy.zip`/`normalize.pkl`, so stages stay loadable on CPU.
- GPU physics uses the Newton solver in float32; CPU uses Gym's PGS in float64. So all evaluation and playback run on the CPU env, and GPU→CPU is treated as a transfer between physics variants, not as an identical simulation. Resuming restores weights, optimizer and normalizer but starts new simulator states; it is not a bit-exact continuation.
- `night.SleepGuard` blocks Windows sleep only while a timed (`hours`) run is active.

**Evaluation and research layers.**
- `evaluation/` holds versioned command scenarios (G1 stand/speeds/stop-restart), runners and statistics. `motion/` holds trajectory and gait metrics. `diagnostics.py` reruns evaluations on 30 independent seeds. `reports.py` writes `report.json`/`report.html`.
- Metrics that can't be determined stay `None`/empty by design; don't invent values such as "humanlikeness".
- `evolution/` (`CampaignManager`, Pareto `selection.py`) manages experiment campaigns. It has no background runner yet (`evolution/runner.py` doesn't exist) and no UI.
