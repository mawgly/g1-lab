# Подключение робота: текущий контракт

Лаборатория расширяется локальными Python-адаптерами. Импорт XML через браузер
пока не реализован. Модель и задача обучения — разные части интеграции.

1. Подготовьте MuJoCo XML, необходимые meshes и описание источника/лицензии.
   Проверьте массы, инерции, суставы, ограничения и приводы на CPU.
2. Создайте Gymnasium-среду задачи: reset, step, observation_space, action_space,
   render, close. Зафиксируйте период управления и значения действий.
3. В `humanoid_sim/tasks/catalog.py` зарегистрируйте RobotSpec и TaskSpec.
   RobotSpec содержит основание, упорядоченные имена суставов/приводов и возможности.
   Фабрика TaskSpec получает `(robot, config)`, возвращает среду. Требования задачи
   должны быть подмножеством возможностей робота.
4. Передайте `identity_factory(robot)` в TaskSpec. Она возвращает robot_id,
   task_id, schema_version=1, model_revision, observation_schema, action_schema,
   normalization_schema и control_dt. При изменении физики, контроллера или порядка
   входов/выходов обновляйте соответствующую версию. Размеры тензоров сами по себе
   не доказывают совместимость. Старый Humanoid сохраняет исходный контракт.
5. `backends` описывает фабрику среды, `training_backends` — доступные способы
   обучения. Для нового адаптера начните с CPU. Запись full_gpu в каталоге сама
   по себе не реализует GPU-среду: для неё требуется отдельная интеграция trainer.
   Тензорные среды регистрируются в `humanoid_sim/backends/registry.py` по тройке
   robot_id/task_id/backend. Trainer получает фабрику оттуда. Наличие фабрики не
   означает прохождение CUDA-проверок: для G1 full_gpu открыт только после тестов
   `tests/test_g1_gpu.py`, замера `humanoid_sim/g1_benchmark.py` и проверки
   сохранения/продолжения. Математику наблюдений и награды держите в одном модуле
   для CPU и GPU, как `tasks/g1_tensor_math.py`.
6. Проверьте короткий цикл обучения, сохранения и восстановления, одинаковый
   результат при фиксированном seed, отображение и причины завершения эпизода.

`TaskSpec.label` — название задачи в интерфейсе, `TaskSpec.jobs` — какие проверки
лаборатории к ней применимы (report, diagnostics, motion, command_suite); кнопки и
`lab_api` берут это из каталога. `asset_identity(..., observation_version=N)`
повышает версию схемы наблюдений, когда меняется их состав.

`TaskSpec.episode_limit_key` задаёт имя параметра ограничения эпизода у фабрики
(по умолчанию max_episode_steps; None — фабрика не принимает лимит).
`evaluation_metrics(initial_info, final_info, terminated)` возвращает метрики
эпизода. Для встроенных задач см. `tasks/evaluation.py`. Без обработчика доступны
награда и длительность; продвижение, падения и успешность не выдумываются.

`config_validator` проверяет и нормализует `task_config` до создания запуска.
По умолчанию разрешён только пустой объект. G1 принимает `reward_weights`
(список и значения по умолчанию — `G1_REWARD_WEIGHTS` в `tasks/config.py`;
конечные неотрицательные коэффициенты до 100). Настройки передаются CPU/тензорной среде и сохраняются в
checkpoint; оценка и просмотр старого checkpoint используют его настройки,
а не текущие настройки запуска. Изменять награду при создании новой ветки можно:
это не меняет размер наблюдений/действий, но сырые награды веток уже несопоставимы.
`tests/test_custom_task_roundtrip.py` демонстрирует регистрацию задачи с одним
мотором, короткое обучение PPO и полный цикл сохранения/загрузки/оценки.

Примеры — фабрики `_arm`, `_g1`, `_humanoid` в каталоге. Общая проверка сохранений
и конфигураций получает контракт из реестра; отдельный список PAIRS не нужен.

## Пока остающиеся ограничения

TaskSpec.playback принимает PlaybackSpec: follow_body (имя тела или None),
target, camera_offset, metric_key, metric_label и необязательный fall_height.
Камера и показатель просмотра передаются браузеру в frame.view. При отсутствии
показателя интерфейс выводит прочерк. Геометрический просмотр требует MuJoCo model/data.

Диагностика походки и GPU-тренеры ещё содержат специальные случаи для встроенных
моделей. Поэтому регистрация нового адаптера уже подключает выбор и CPU-фабрику,
но пока не гарантирует полный цикл для произвольного робота. Следующие работы:
семантические роли тел, расширенная диагностика, проверка backend по модели,
и интеграционный тест четвёртой модели без изменений общих модулей.
